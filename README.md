## 一、系统是什么

一套给仓库/质检在手机上使用的**次品登记 + 退货/退款跟进**工具，对接 **聚水潭 ERP** 和 **1688 采购后台**：

- **次品收集.html**：扫码登记采购单号、逐件扫次品 SKU、拍照上传、查看每条记录的退款/退货状态、一键发起退货
- **退货面单.html**：配套的退货面单打印工具（76mm×130mm 面单）
- **return-worker**（Cloudflare Worker）：后台实时调用**聚水潭 API** 创建采购退货单
- **yto-proxy**（Cloudflare Worker）：圆通快递面单 API 代理
- **data/***.json**：供应商/SKU/1688订单号等映射数据

## 三、系统如何运转（全链路）

```
仓库手机端（次品收集.html）
   │ ① 扫采购单号 + 逐件扫SKU + 拍照上传 → Supabase（defect_reports + 图片存储）
   │ ② 点"一键退货" → 给记录打 [退货:待处理] 标签（等待后台处理）
   ▼
后台（return-worker / 定时任务）
   │ ③ 实时调用聚水潭 API：按供应商合并 → 创建采购退货单（shop_id=21571486 外贸采购退货店铺）
   │ ④ 回写 [退货:已下单:内部单号] 到记录
   │ ⑤ 每2小时同步 1688 退款进度 / 聚水潭退货单状态 → 更新记录标签
   ▼
前端自动刷新展示：卖家同意 / 买家退货 / 卖家收货 / 完成 / 失败 / 异常…
```

### 🔵 1688 采购单流程
1. 仓库扫码登记次品 → 拍照上传
2. 点"一键退货" → 系统**跳转 1688 后台对应订单页**（人工提交退款申请，带图片凭证）+ 打标签创建聚水潭退货单
3. 等卖家同意 → 填快递单号 → 打面单寄回 → 卖家收货 → 退款完成
4. 退款进度由后台每 2 小时同步回前端展示

### 🟡 非 1688 采购单流程
1. 仓库扫码登记次品 → 拍照上传
2. 点"一键退货" → 后台自动创建聚水潭采购退货单（约 1~2 分钟）
3. 去聚水潭"外贸采购退货"店铺打面单发货 → 已下单（内部单号）= 完成

## 四、标签状态机（前后端通信方式）

记录备注里用方括号标签传递状态，前端解析展示：

| 标签 | 含义 |
|---|---|
| `[退货:待处理]` | 已发起退货，等待后台创建订单 |
| `[退货:已下单:内部单号]` | 聚水潭退货单已创建 |
| `[退货:失败]` | 创建失败（如地址缺电话） |
| `[退款:状态:退款ID]` | 1688 退款进度（等待卖家同意 / 卖家拒绝 / 退款成功…） |
| `[1688:...]` | 标记为 1688 来源采购单 |
| `[系统:重新匹配]` | 触发后台重新匹配供应商 |

## 五、配置说明（以后调整只改这些地方）

### 前端配置 —— `次品收集.html` 顶部 `APP_CONFIG`
```js
const APP_CONFIG = {
    supabaseUrl:  'https://xxx.supabase.co',      // Supabase 地址
    supabaseKey:  'eyJ...',                       // Supabase anon key
    tableName:    'defect_reports',               // 记录表名
    photoBucket:  'defect-photos',                // 图片存储桶名
    fetchLimit:   500,                            // 列表一次加载条数
    returnShopId: '21571486',                     // 聚水潭退货店铺 shop_id
    backendBaseUrl: '',                           // 预留：后端直连地址（暂空）
};
```

### 后端配置 —— `backend/return-worker/wrangler.toml`
- `JST_APP_KEY` / `JST_BASE_URL` / `RETURN_SHOP_ID` / `SUPABASE_URL` / `SUPABASE_KEY` / `STYLE_MAP` / `RETURN_ADDR_MAP` 为环境变量
- **`JST_APP_SECRET` 和 `JST_ACCESS_TOKEN` 不要写进 toml**，用 `wrangler secret put` 设置（详见 `backend/README.md`）

## 六、部署

1. **前端**：把整个 `次品收集系统/` 目录推到 GitHub Pages（或任意静态托管），`次品收集.html` 即为入口
2. **后端**：进入 `backend/return-worker`、`backend/yto-proxy`，`npm i -g wrangler` 后 `wrangler deploy`（详细步骤见 `backend/README.md`）
3. **数据文件**：4 个 `*.json` 必须和 `次品收集.html` 放在同一层（网页用相对路径加载）。
   其中 `sku_info_map.json` / `return_style_map.json` / `return_addr_map.json` 可用
   `backend/sync-jst-maps.js` 从**聚水潭接口**自动生成（商品颜色/码数、供应商、退货地址
   均以聚水潭为准），生成后直接覆盖同名文件即可

### 待确认（与 SOP 有出入、需你和开发确认的点）
1. **1688 记录的聚水潭退货单**：`return-worker/src/index.js` 中 `getDefectRecords()` 会过滤掉带 `[1688:` 标签的记录。也就是说 1688 采购单目前**不会**由该 worker 创建聚水潭退货单，只有跳转 1688 后台人工退款。这与 SOP 中"1688 也创建聚水潭退货单（回写内部单号）"的描述不一致——需要确认 1688 流程的聚水潭建单由谁完成。
2. **"实时创建"的实现位置**：前端"一键退货"实际是**打标签**，真正实时调用聚水潭 API 的是后台（定时任务调 worker）。用户感知约 1~2 分钟，符合"约1分钟内自动创建"。如果你希望点击后**立即**出结果（毫秒级），可以把 `APP_CONFIG.backendBaseUrl` 填上并让前端直接调 worker。
3. **每 2 小时同步**：由仓库外的定时任务执行，未包含在本仓库。SOP 说可接受；如需要可在前端加"手动刷新"按钮（待后续需求）。
